A seam is where a test replaces production behaviour. Pick them well and the suite reads like documentation; pick them badly and every refactor rewrites a hundred files that were never about the thing you changed.

## The rule I keep coming back to

Put the seam at a boundary you would have to draw anyway — the network, the clock, the filesystem — and nowhere else.

<Callout kind="note" title="A quick test for a seam">
  If a behaviour-preserving refactor breaks the test, the seam was inside the
  implementation rather than at its edge.
</Callout>

## Injection beats module mocking

```ts title="collection.ts"
export const createArticleOperations = (options: {
  readonly manifest: readonly ArticleManifestEntry[];
  readonly today: Temporal.PlainDate;
}) => {
  // Everything below is pure, so a test needs no mocking at all.
};
```

Passing the boundary in makes the fake ordinary code. Mocking the module makes the fake a fact about the file system, and facts about the file system leak into every test that happens to import the same thing.

## What this buys

- [x] A refactor that preserves behaviour preserves the suite.
- [x] Failures name a contract instead of a call.
- [ ] Freedom from ever writing a module mock again — that one is aspirational.

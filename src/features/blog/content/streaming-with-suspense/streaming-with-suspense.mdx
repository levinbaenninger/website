A streamed page is a promise that the shell will arrive early and the rest will catch up. Visitors take that deal happily right up to the moment the catching up moves something they were already reading.

## The shell is a design decision

Whatever renders before the boundary resolves is not a loading state — it is the page, for as long as the slowest query takes. Treating it as throwaway is how skeletons end up a different height from the content they stand in for.

<Steps>
  <Step title="Name the shell">
    Decide what a visitor sees with zero data. If the answer is "a spinner", the
    boundary is drawn in the wrong place.
  </Step>
  <Step title="Reserve the space">
    Give the fallback the dimensions of the thing it replaces. A boundary that
    resolves without moving anything is invisible, which is the goal.
  </Step>
  <Step title="Push the boundary down">
    The smaller the streamed region, the smaller the shift it can cause.
  </Step>
</Steps>

## Reading the seam

```tsx title="app/dashboard/page.tsx"
export default function Page() {
  return (
    <section>
      <Heading />
      <Suspense fallback={<ActivitySkeleton />}>
        <Activity />
      </Suspense>
    </section>
  );
}
```

<Callout kind="warning" title="Skeletons are a contract">
  A skeleton that does not match its content's height converts a fast page into
  a janky one. If you cannot predict the height, do not stream that region.
</Callout>

## When not to stream

If the data is fast and cacheable, streaming adds a boundary, a fallback and a shift for no gain. Measure first — [budgeting images](/blog/budgeting-images) is usually the larger win on a content page.
